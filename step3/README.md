# step3：関数を呼ぶと「戻り先メモ」が積まれる

> この回もコードなし。攻撃の「的（まと）」がどこに用意されるかを、絵で理解する。

## つかむこと

`main()` の中で `vulnerable()` のような関数を呼ぶと、その関数専用の作業スペース
（**スタックフレーム**）がメモリに用意される。関数が終わると片付けられる（使い捨ての作業机）。

その机の上に、次の2つが**隣り合って**置かれる：

```
   vulnerable() のスタックフレーム（関数を呼ぶと作られる）
   ┌─────────────────────────────────────────────┐
   │ [buf ＝ 入力を入れる箱][...]   [ 戻り先メモ ]  │
   │  └─ グレーの箱たち ─┘          └ 中身は番地 ┘ │
   └─────────────────────────────────────────────┘
                                         │
                                         └→ 終わったら main の番地へ戻る
```

- **buf**：その関数で使う変数。入力を受け取る入れ物。step2 の `char c` の複数箱版。
- **戻り先メモ**：「vulnerable() が終わったら main のどこへ戻るか」という**番地**が入っている。
  中身が番地 ＝ step1 で言った「ポインタ的な値」。

## なぜ隣同士なのか（step3 で一番の納得ポイント）

1. スタックは**一本の連続した棚**で、置かれるものは連続した番地に、隙間なく詰めて並ぶ（連番的）。
2. 「buf の隣に戻り先メモを置こう」と誰かが選んでいるのではない。
   関数を呼ぶ `call` 命令が、**ハードウェアの決まりごととして戻り先メモを自動で積む**。
   その後で関数が buf をすぐ隣に取る。だから隣接は「設計上そうなる」結果。

## 「離して置けばいいのでは？」への答え

- **真の原因は“隣接”ではなく“無チェックの書き込み”**。
  C は buffer のサイズを実行時にチェックしないので、遠くに離しても
  十分長い入力は間の物を踏み潰して戻り先メモに届く。距離は解決にならない。
- 戻り先メモを棚から別管理にすると、超高頻度の `call`/`ret` が遅くなる。速度のためにこの配置。

## 「間に見張りを置けば？」への答え → 実在する

buf と戻り先メモの**間に、毎回変わる秘密の値**を置くのが **スタックカナリア**。
関数を抜ける直前にその値が無事かチェックし、書き換わっていたら侵入とみなして強制終了する。
→ `-fno-stack-protector` は、このカナリアを外すフラグだった。

## さらに本質的な防御：安全な言語を使う

buffer のサイズを超える書き込みを**言語が許さなければ**、このバグ自体が起きない。
Go / Rust / Java / Python / C#（JS/TS も）は範囲チェック付きで、範囲外は例外や panic になる。
C/C++ は「速度と自由のためにチェックを省く」思想なので、この危険が残る。

→ 次（step4）で、実際に buf を溢れさせて壊してみる。
